# Lingxi Custom Experience

LingxiIdentity ships a small, independent SPA under `experience/`. It is
compiled against the Logto **1.33.0 Experience API** contract and overlaid onto
the pinned Logto image at build time. The SPA is intentionally not part of the
LingxiLearn Next.js application and does not use Better Auth.

## Request boundary

The browser is redirected to Logto by the existing BFF (`/auth/login`,
`/auth/register`, or `/auth/forgot-password`). Once Logto creates its OIDC
interaction, the SPA calls only same-origin Experience API endpoints:

```text
GET  /api/.well-known/experience
GET  /api/experience/interaction
PUT  /api/experience
POST /api/experience/verification/password
POST /api/experience/verification/verification-code[/verify]
POST /api/experience/identification
POST /api/experience/profile
POST /api/experience/submit
POST /api/experience/verification/social/:connectorId/*
```

`experience/src/lib/experience-api.ts` is the only module that knows these
paths. Components submit credentials to Logto for the active interaction; the
SPA never calls the LingxiIdentity Account API and never exchanges OIDC codes.
The `/api/experience/submit` response is the Logto-generated continuation URL,
which sends the browser back to the existing BFF callback. The BFF performs the
authorization-code exchange and stores tokens only in its encrypted,
server-side session.

## Local build

```powershell
Set-Location experience
npm ci
npm run check
npm run build
```

From the repository root the equivalent reproducible target is
`make experience-build`.

The result is `experience/dist/index.html` plus hashed assets. The static bundle
is ignored by Git and rebuilt in the custom image build.

## Custom image

`deployment/logto/Dockerfile.custom` uses a two-stage build:

1. Node 22 installs the locked `experience/package-lock.json`, type-checks and
   builds the SPA.
2. `ghcr.io/logto-io/logto:1.33.0` is used unchanged as the runtime image and
   receives only `packages/experience/dist` from stage one (the workspace path
   used by the published v1.33.0 image).

Compose uses `lingxi-logto:1.33.0-experience` by default for both `logto` and
`logto-migrate`, so both services have the same upstream baseline. Build and
start it with:

```powershell
docker compose --env-file .env -f deployment/compose.yaml build logto logto-migrate
docker compose --env-file .env -f deployment/compose.yaml up -d postgres logto
```

The image health check remains Logto's `/api/status`. A deployment should run
the existing migration profile before starting the BFF on a fresh database.

## Rollback

The custom UI can be removed without changing the database or BFF. Set the
following in `.env`, then recreate only the Logto services:

```text
LOGTO_IMAGE=ghcr.io/logto-io/logto:1.33.0
```

This restores the upstream Experience bundle. Reverting to the custom image is
the inverse change. Do not use an unpinned `latest` tag.

## Security notes

- Passwords and verification codes exist only in the active form and request;
  they are not written to localStorage/sessionStorage or application logs.
- The only browser storage used by the SPA is a short-lived social callback
  state and verification ID. It contains no token or credential.
- Experience cookies and interaction state remain Logto-owned. The SPA does not
  create an authentication session.
- Social callbacks are verified against the state generated by the adapter and
  are submitted back to Logto. Provider SDKs and token exchange are not loaded
  in LingxiLearn.
- Redirect continuation is returned by Logto after its OIDC interaction checks;
  the SPA accepts only `http`/`https` URLs and does not construct a redirect
  from user-entered form values.

The adapter deliberately isolates the version-specific Experience contract. A
future Logto upgrade must update `LOGTO_UPSTREAM_VERSION`, review the adapter
against the new upstream API, and rerun the build plus a fresh-browser smoke
flow before rollout.
